# IRLIX Buyer Radar — контекст продукта, решения и план MVP

**Статус:** согласованное направление; Buyer Radar как самостоятельный модуль **ещё не реализован**.  
**Дата фиксации:** 2026-10-23.  
**Репозиторий:** [zampolit73/zampolit73project](https://github.com/zampolit73/zampolit73project) (публичный).  
**Сайт:** https://zampolit73.duckdns.org  
**Исследования:** https://zampolit73.duckdns.org/projects/irlix-sales/research

> Этот документ — **проектный handoff из обсуждения**. Он сохраняет цели, продуктовые решения, ограничения и следующий шаг, чтобы продолжить разработку в новом чате. Это **не** архив всей переписки и **не** утверждение, что идеи из раздела «План» уже внедрены. Секретов, персональных данных, закрытых CRM-заметок здесь быть не должно.

## 1. Главная цель и принципиальное решение

Компания «Ирликс» продаёт IT-аутстаффинг и заказную разработку. Главная бизнес-цель проекта — **увеличить количество новых потенциальных прямых заказчиков, повысить точность выявления спроса и помочь менеджерам выходить на релевантных ЛПР**.

**Это разведка продаж, а НЕ CRM.**

- В компании уже есть действующая CRM. **Никаких интеграций с ней в этом MVP не планируем.**
- **Не строить** здесь воронку, сделки, переписки, постановщик задач, pipeline, полноценный учёт активности или «единую карточку клиента с историей продаж».
- Не объединять насильно существующую базу IRLIX Sales, IRLIX Intelligence и Vacancy Source в единую CRM.
- «Взять в работу» как CRM-процесс, персональные task-менеджеры, напоминания о сделках и отчётность по конверсии **не входят в приоритетный backlog**.
- Допустим простой экспорт XLSX/CSV/JSON для ручного переноса в действующую CRM, без API-интеграции.
- Основные выходы радара: **название прямого заказчика, проверяемый сигнал спроса, уровень доказательности, соответствие компетенциям Ирликса, ссылка и причина для первого обращения**.
- Контакты ЛПР — следующий этап детального исследования в ChatGPT по существующему навыку; не подменять подтверждённый спрос наличием телефона.

## 2. Денежное ограничение — обязательное

**Нулевая стоимость новых подписок / AI API / инфраструктуры.**

Уже имеются VPS и аккаунты ChatGPT у команды. Использовать их, а не покупать новые сервисы.

- Laravel 13 / PHP 8.3, Vue 3 / Inertia, SQLite, существующий VPS (Ubuntu, Nginx, PHP-FPM, без Docker).
- Laravel scheduler / jobs / database queue, SQLite, лёгкий HTTP/HTML/XML/RSS-парсинг там, где источник разрешает и технически позволяет.
- Существующие Vacancy Source и Telegram-бот.
- ChatGPT менеджеров выполняет **глубокие** исследования вручную по запросу; сервер **не** вызывает OpenAI API для каждой компании.
- Не покупать платные поисковые API, парсеры/прокси, антикапчу, платные базы закупок или платные тарифы торговых площадок.
- Не обходить капчи, авторизацию, robots/ToS или антибот-защиту. Если источник не предоставляет пригодный публичный доступ, использовать ручной ввод ссылки или отказаться от автоматизации.
- «Бесплатно» значит **0 ₽ новых регулярных расходов**, не обещание отсутствия затрат на уже существующий VPS/ChatGPT или бесплатного доступа ко всем коммерческим тендерам.

## 3. Что УЖЕ реализовано и испытано

### 3.1. IRLIX Intelligence

- Существует готовый **10-раздельный формат исследования** компании: юрлицо/финансы; признаки внешней IT-разработки; тендеры; подрядчики/проекты; технологии; ЛПР и профессиональные профили; маршрут закупок; стратегия выхода; оценки и источники.
- Навык/инструкция: [docs/IRLIX_ANALYST_CHATGPT.md](IRLIX_ANALYST_CHATGPT.md).
- JSON v1: [docs/IRLIX_COMPANY_REPORT_EXAMPLE.json](IRLIX_COMPANY_REPORT_EXAMPLE.json); описание [data/company-reports/README.md](../data/company-reports/README.md).
- Публичные исследования из GitHub и **приватные импорты в SQLite** отображаются в одном разделе `/projects/irlix-sales/research`; импортированные исследования **не** публикуются в Git.
- Поддерживаются загрузка через сайт, версионирование по ИНН/ID, просмотр автора, история ревизий, экспорт JSON.
- Реальные исследования в пилоте: Haier/«ХАР», «Золотое яблоко» / GA Tech Team, «Подружка» / ООО «Табер Трейд».

### 3.2. Telegram-доставка исследований

Работает цепочка:

```text
Менеджер в ChatGPT → JSON v1 → Telegram-бот (документ)
→ проверка JSON и совпадений → кнопка «Сохранить/Обновить»
→ SQLite на VPS → карточка в IRLIX Intelligence
```

- Бот использует привязку Telegram к аккаунту сайта; файлы <= 256 КБ; подтверждение действует 30 минут.
- История версий и защита от повторного сохранения протестированы на реальном импорте «Подружки» версии 1 и версии 2.
- При успешном сохранении бот возвращает номер версии и ссылку; после подтверждения кнопки скрываются.
- Файлы через Telegram проходят облако Telegram — особо чувствительное загружать напрямую на сайт.

### 3.3. Vacancy Source

- В репозитории уже существует проект расследования IT-вакансий и выявления конечного заказчика.
- Имеются Telegram Reader, Habr Career / публичные web-источники и детерминированная оценка сигналов — **проверить текущую реализацию в коде** перед переиспользованием.
- Vacancy Source — **источник косвенных сигналов**, а не доказательство, что компания покупает аутстаффинг.

См. [docs/VACANCY_SOURCE.md](VACANCY_SOURCE.md), [docs/ARCHITECTURE.md](ARCHITECTURE.md).

## 4. Каким должен быть Buyer Radar

Отдельный раздел **«Радар заказчиков»** внутри существующего сайта (желательно рядом с IRLIX Intelligence), а не отдельная CRM.

Основной вопрос: **«Какие новые прямые заказчики стоит исследовать и кому написать сейчас — с какими доказательствами?»**

Предлагаемая карточка кандидата содержит:

- Компания / бренд; ИНН **только если подтверждён**; отрасль; сайт (если установлен).
- Источник, дата публикации и дата обнаружения, прямая ссылка.
- Тип сигнала: тендер IT-услуг, привлечение внешнего IT-подрядчика, спрос через вакансии, технологический проект.
- Что именно обнаружено: стек/роли/объём, формат услуг, условия (если действительно опубликованы).
- **Тип подтверждения**: прямое свидетельство аутстаффинга, подтверждённая внешняя разработка, косвенный найм, гипотеза.
- Две **раздельные** оценки: (1) надёжность доказательства внешнего спроса, (2) коммерческая полезность Ирликсу.
- Почему лид заслуживает внимания, какое направление Ирликса предложить; что остаётся проверить.
- Состояние проверки сигнала: новое / проверено / шум / не подходит. Это *качество разведданных*, не стадия сделки.
- Возможность открыть оригинальный источник, запустить глубокий анализ в ChatGPT и затем импортировать JSON существующим способом.

**В интерфейсе:** список/фильтры по периоду (7/30 дней), источнику, технологии, типу сигнала, рейтингу, наличию ИНН и степени подтверждения. Сортировка по доказанному спросу и свежести. Счётчик новых **уникальных** компаний; лёгкая мобильная версия (320px).

## 5. Где искать (от простого к сложному)

Начать всего с **2–3 технически и юридически доступных семейств источников**. Не обещать охвата всего рынка РФ.

| Тип | Польза | Решение для MVP |
|---|---|---|
| Открытые государственные закупки: ЕИС / доступные 44-ФЗ и 223-ФЗ публикации | Фактические IT-закупки, роли, бюджет, сроки, заказчик | Сначала исследовать доступный публичный формат (RSS/XML/страница). Если доступ ограничен — ручной URL |
| Публичные кейсы IT-аутстафферов, разработчиков и интеграторов | Связь «поставщик → заказчик → проект» | Высокий приоритет. Сохранять ссылку и **отличать** проектный аутсорс от IT-аутстаффинга |
| Habr Career / существующий Vacancy Source | Стек, расширение команд, возможные новые проекты | Вторичный усиливающий сигнал; обычная вакансия не доказывает внешнюю закупку |
| Bidzaar, другие коммерческие площадки | Потенциально высококачественные признаки T&M / внешней разработки | Публичные ссылки и ручное добавление; автообход **только после проверки** легального, технически доступного режима |
| Публичные сайты компаний, пресс-релизы, новости | Открытие цифровых проектов и бюджетных направлений | Дополнительные источники, не основа скоринга |

Платные агрегаторы и демо-подписки не должны становиться обязательной частью инфраструктуры. Не извлекать неизвестный бюджет, победителя, ставки, адреса или юрлицо из предположений.

## 6. Пример скоринга — ГИПОТЕЗА, НЕ готовое правило

Предложенная стартовая модель (проверить пилотом; **ещё не утверждена как формула**):

| Сигнал | Максимум |
|---|---:|
| Прямая открытая закупка IT-аутстаффинга / выделенных IT-специалистов | 40 |
| Подтверждённые публичные отношения с внешним IT-подрядчиком | 25 |
| Свежесть и масштаб потребности | 15 |
| Совпадение с компетенциями Ирликса | 10 |
| Проверяемый канал выхода на IT-покупателя | 10 |
| **Итого** | **100** |

**Никогда не считать:** «массово нанимают Java-разработчиков» = «покупают Java-аутстаффинг».

Отдельно показывать **уровень доказательности**:
- A: прямой первичный источник закупки или подтверждённого внешнего IT-проекта;
- B: открытый косвенный сигнал;
- C: непроверенная гипотеза.

Коммерческий балл 0–100 **не** является вероятностью заключения договора. Текущий рейтинг A/B+/B/C/D из полноформатного IRLIX Intelligence не должен автоматически означать «подтверждённый покупатель аутстаффинга». В UI эти оси должны быть различимы.

Отсев шума: агентства и рекрутеры, посредники без подтверждения конечного клиента, архивные тендеры, неподходящие стеки, повторные публикации одной закупки и голый штатный найм.

## 7. Архитектурная идея (ещё не реализована)

```text
Проверяемые общедоступные URL / разрешённые фиды
        ├── государственные IT-закупки
        ├── публичные кейсы IT-подрядчиков
        └── Vacancy Source (дополнительный сигнал)
                    ↓
       лёгкие задания Laravel (rate limits, таймауты)
                    ↓
      извлечение метаданных + точные ссылки
                    ↓
        очистка, дедуп, распознавание заказчика
                    ↓
      SQLite: кандидаты, сигналы, источники, статусы
                    ↓
       прозрачный скоринг и фильтры на сайте
                    ↓
       подборка Telegram (по запросу / расписанию)
                    ↓
   менеджер выбирает компанию → анализ в ChatGPT
                    ↓
             JSON → Telegram → SQLite
```

Возможные новые таблицы (предложение, **не текущая схема**):
- `radar_sources`: имя/URL/тип, режим доступности, частота, активность, last_scan / last_error;
- `radar_signals`: тип, исходный URL, хэш/внешний ID, заголовок, сниппет, опубликовано/обнаружено, technology tags, evidence status, company candidate id;
- `radar_companies`: нормализованное название, ИНН nullable, сайт nullable, агрегированный score, first/last_seen, reason summary;
- `radar_signal_reviews` **только если нужно** сохранить отметки «проверено / шум»; не строить CRM.

Хранить достаточно метаданных и ссылок; не копировать целые платные статьи, закрытые тендерные документы или персональные данные. Дедуп по каноническому URL/ID закупки и по подтверждённому ИНН, когда он доступен. Связи с другими проектами через аккуратные ссылки, а не миграцию их данных в CRM.

Планировщик: рассмотреть **два коротких запуска в сутки**, но включать только после теста нагрузки и разрешённого режима доступа. Ручной запуск по кнопке и ручное добавление URL полезны с первой версии.

## 8. Roadmap — согласованный порядок

### Этап 0. Проверка источников (следующая задача)

1. Проверить доступность **реальных** публичных точек сбора минимум для двух источников (тендеры, кейсы подрядчиков), без платных аккаунтов.
2. На небольшой репрезентативной выборке измерить долю шума и целевых сигналов, доступность ссылок, наличие конечного юрлица/ИНН.
3. Зафиксировать, какие источники пригодны к автоматическому обновлению, а какие — только к ручному импорту URL.
4. Утвердить минимум полей «карточки сигнала», типы ошибок и ограничения по скорости обхода.

### Этап 1. Минимальный радар

- Лёгкий сбор из **2–3 подтверждённо доступных** источников.
- Нормализация и дедуп компаний, сохранение ссылок и доказательств.
- Прозрачный скоринг, ручная проверка качества, фильтры 7/30 дней, стек и сигнал.
- Возможность добавить URL вручную и открыть оригинал.
- Юнит/feature-тесты, мобильный интерфейс и бережное использование VPS.

### Этап 2. Глубокое исследование без AI API

- «Исследовать в ChatGPT» — подготовить конкретный промпт/краткий пакет доказательств с URL для менеджера.
- После исследования менеджер уже существующим способом загружает JSON через Telegram/сайт.
- Показывать «исследование уже есть» по проверенному ИНН/ID, но **не** делать CRM.
- Встроить отчётность о том, насколько полезен радар: новые уникальные компании, подтверждённые IT-сигналы, количество компаний с каналом выхода.

### Этап 3. Telegram-подборки и уточнение ранжирования

- Только новые, качественные сигналы; у каждого — почему интересен и исходная ссылка.
- Периодичность — по реальному объёму сигналов; не спамить.
- Улучшать правила на основе доли ручного «шум / потенциальный покупатель».
- При необходимости добавить новые открытые источники по одному.

## 9. Критерии успеха пилота

Первые 2–3 недели, пробный корпус около **50–100 кандидатов**, измеряем:

1. Доля новых **уникальных прямых заказчиков**, а не публикаций/посредников.
2. Доля подтверждённых внешних IT-закупок/проектов; сколько лишь штатный найм.
3. Сколько кандидатов соответствуют стекам и предложениям Ирликса.
4. Сколько потенциальных целей менеджеры сочли пригодными для первого контакта.
5. Сколько источников стабильно доступны без платных API и обхода ограничений.

Ориентир «10 перспективных компаний в неделю» — **экспериментальная цель, не обещанный результат**. Фальшивые или нерелевантные лиды недопустимы даже при большом количестве записей.

## 10. Что НЕ делать без нового решения

- Полноценную CRM, сделки, активности, задачи, интеграцию с текущей CRM.
- Автоматическую рассылку email/LinkedIn, выдумывание деловых контактов.
- Автоматический анализ каждой компании платным LLM API.
- Неограниченный парсинг сети, обход запретов, постоянные тяжёлые crawlers.
- Отождествлять штатные вакансии и внешний спрос; объявлять всех подрядчиков аутстафферами.
- Публиковать пользовательские SQLite-исследования или приватные коммерческие сведения в публичном GitHub.
- Считать предложения из этого документа реализованными функциями.
- Переписывать уже действующий Vacancy Source или существующий импорт JSON без отдельной необходимости.
