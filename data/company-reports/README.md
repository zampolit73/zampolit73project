# IRLIX Intelligence — публичные исследования компаний

В этой папке будут появляться JSON-отчёты, созданные AI-аналитиком по запросу из обычного чата ChatGPT.

## ВАЖНО: репозиторий публичный

Все файлы, их прошлые версии и Git history доступны посторонним.
**Не размещать** здесь:
- контакты, полученные из непубличных CRM/переписки, личные телефоны/email;
- договоры, ставки, планы переговоров, внутренние заметки и клиентские секреты;
- непроверенные персональные утверждения или конфиденциальные сведения;
- пароли, токены и ключи.

Можно сохранять подтверждённые публичные сведения о компаниях, публичных профессиональных
представителях (с прямой ссылкой на открытый источник), закупках и вакансиях.
Любые гипотезы должны быть помечены как гипотезы.

## Как опубликовать отчёт из ChatGPT

1. Выполнить исследование и собрать ссылки на конкретные публичные источники.
2. Прочитать инструкцию: \`docs/IRLIX_ANALYST_CHATGPT.md\`.
3. Найти существующий файл компании по ИНН или устойчивому идентификатору.
4. Создать или обновить \`data/company-reports/<id>.json\` через подключённый GitHub.
5. Дождаться CI и деплоя \`main\`. Не сообщать об успешной публикации до завершения workflow.
6. Открыть \`https://zampolit73.duckdns.org/projects/irlix-sales/research\` (admin).

Текущий MVP **не синхронизирует отчёт напрямую в SQLite и не заполняет автоматически CRM-карточку**.
Он отображает отчёты из GitHub после стандартного деплоя сайта.
Создание нового отчёта не означает подтверждённую закупку.

Шаблон формата: \`docs/IRLIX_COMPANY_REPORT_EXAMPLE.json\`.
Не добавляйте в эту папку «пример» в виде фиктивной компании.

Отчёты идентифицируются по имени файла (от 3 до 80 латинских строчных букв,
цифр и дефисов). \`id\` внутри файла должен совпадать с именем файла без \`.json\`.
По возможности используйте \`inn-<10-or-12-digits>\` — это помогает избежать дублей.
Пример: \`inn-7707083893.json\`. Если ИНН неизвестен, используйте стабильный
англоязычный идентификатор компании и не переименовывайте его после создания.

## Схема

Обязательны: \`schema_version=1\`, \`id\`, \`company.name\`,
\`researched_at\` (UTC ISO 8601 \`YYYY-MM-DDTHH:MM:SSZ\`).

Основные поля:
- \`company\`: \`name\`, \`inn\`, \`website\`, \`industry\`
- \`summary\`: главный вывод с оговорками
- \`outstaff_demand\`: \`assessment\` = \`confirmed|likely|unclear|no_evidence\`;
  \`explanation\` — конкретный источник/причина
- \`technologies\`: массив технологий, только при наличии основания
- \`contractors\`: \`name\`, \`relationship\` = \`confirmed|hypothesis\`, \`note\`
- \`decision_makers\`: \`name\`, \`role\`, \`public_url\`; только открытые профили
- \`evidence\`: \`title\`, \`url\`, \`finding\`; URL только HTTP(S)
- \`recommendation\`: **публично допустимая** общая рекомендация
- \`open_questions\`: массив оставшихся вопросов

### Контроль качества
- \`confirmed\` ставить только при прямом доказательстве закупки; одна вакансия не доказывает аутстаффинг.
- \`likely\` для косвенных сигналов, \`unclear\` при недостатке данных, \`no_evidence\` если подтверждений не найдено.
- Не придумывать ИНН, ЛПР, подрядчика, URL, дату или результат.
- Ссылка на источник должна поддерживать именно заявленный факт.
- Ссылки на публичную информацию об ЛПР не являются разрешением публиковать их частную переписку.
- В GitHub сохранять те же выводы, что и в отчёте пользователю; при ограничениях GitHub не утверждать, что запись произошла.
